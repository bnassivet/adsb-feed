# Tool-ranking evaluation

Does a small decision model pick the tools a request needs, well enough that the
agent can bind ten tools instead of forty? This directory answers that with MLflow
datasets and `mlflow.genai.evaluate`. The ranker itself is
`src/adsb_agent/tool_ranker.py`; design and background are in
`../../adsb-pulsar-client-desktop/docs/plans/2026-11-11-agent-tool-ranking.md`.

Needs the `eval` extra and the MLflow server on `:5010`:

```bash
cd rust/adsb-agent
uv sync --all-extras
```

## Layout

| Where | What |
|---|---|
| `eval/` | shared: datasets and MLflow setup (`common.py`), the main set (`data/labels.jsonl`), the tool surface snapshot, the tool ranker and the main agent's first step (`eval_ranker.py`, `eval_agent_step.py`), the prompt-cache experiment, `results/` |
| `eval/fastpath_agent/` | the desktop fast path experiment: gates, veto, executors, the service's own path, its label sets and fixtures, and its record `FAST_PATH_EXPERIMENT.md` |

Every script runs as a file from `rust/adsb-agent`, in either folder
(`uv run python eval/fastpath_agent/eval_route.py`). The subpackage imports the
shared modules, never the reverse (`tests/fastpath_agent/test_eval_layout.py`).
The experiment's tests, and those of the fast path service, are in
`tests/fastpath_agent/`.

## Workflow

| Step | Command | Result |
|---|---|---|
| 1. Snapshot the tools production sends | `uv run python eval/snapshot_tool_surface.py` | `fixtures/tool_surface.json` |
| 2. Mine real questions from the agent's traces | `uv run python eval/mine_traces.py` | `data/candidates.jsonl` (not ground truth) |
| 3. **Review the labels by hand** | edit `data/labels.jsonl` | the ground truth |
| 4. Publish a dataset version | `uv run python eval/upload_dataset.py` | dataset `adsb-tool-selection-v<N>` |
| 5. Stage A: rank quality, no LLM | `uv run python eval/eval_ranker.py --wording baseline --top-k 6 8 10 12 15` | one MLflow run per k |
| 6. Stage B: the LLM's first tool choice | `uv run python eval/eval_agent_step.py --mode full --limit 30`, then `--mode ranked` | two runs to compare |

Runs land in the experiment `adsb-agent-tool-ranking`, kept apart from the agent's own
`adsb-agent` experiment so evaluation traces never mix with real usage.

## Labels

One JSON object per line in `data/labels.jsonl`:

- `question`, `history` — the request and the user messages before it (a follow-up such
  as "and now?" is meaningless alone).
- `expected_tools` — every tool the agent needs across the **whole chain**, not just the
  first call. "How many aircraft in the last hour" needs `getCurrentDateTime` *and*
  `getAircraftSummary`.
- `any_of` — groups of interchangeable tools; one from each group is enough.
  "Traffic statistics for the last 2 hours" can be answered with `getAircraftSummary`,
  `getFlightSummary` or `getTimeDistribution`.
- `observed` (trace rows only) — what the agent actually called. Kept for the reviewer;
  it is not the label, because the agent was sometimes wrong.

`candidates.jsonl` is regenerated by step 2 and is only raw material. Adding traffic to
the agent and re-mining does not touch `labels.jsonl`.

## Dataset versions

Each version is its own MLflow dataset, `adsb-tool-selection-v<N>`, frozen once
published. Open-source MLflow has no immutable dataset versions
(`get_dataset(version=...)` is Databricks-only) and `merge_records` edits in place, so
without this a label fix would silently change what every earlier run was measured on.

- The dataset is tagged with the SHA-256 of the `labels.jsonl` it was built from, the
  git commit, and record counts. `upload_dataset.py --list` shows the published versions.
- Publishing the same labels again does nothing. Publishing **changed** labels is
  refused until you bump `DATASET_VERSION` in `common.py`.
- To release a new version: edit `labels.jsonl`, bump `DATASET_VERSION`, commit both,
  run `upload_dataset.py`.
- Evaluations read the published dataset by default and log its name and labels hash as
  run parameters. `--dataset-version N` re-runs against an older version; `--data labels`
  evaluates the working copy of `labels.jsonl` for drafts not yet published.

## Validation requests

`fastpath_agent/data/validation_labels.jsonl` holds 176 requests that no description, threshold
or wording was tuned against (81 direct commands, 95 agent requests). It is a
second labels file, not a dataset version: select it with `ADSB_EVAL_LABELS` and
`--data labels`. Run and result-file names then end in `-validation_labels`.

```bash
export ADSB_EVAL_LABELS=eval/fastpath_agent/data/validation_labels.jsonl
uv run python eval/eval_agent_step.py --mode full --context-placement user --data labels
uv run python eval/fastpath_agent/eval_fast_path_service.py --data labels
```

- `source: trace` (21): requests mined from the agent's traces after the main
  set was labelled, mostly voice transcripts, kept verbatim.
- `source: authored` (155): written before their author read the packaged
  descriptions or the main set's questions; five that turned out identical to a
  main-set question were dropped. `tag` says what kind: `near_tool` is a question
  or remark that sits next to a direct tool, `needs_lookup` a command that needs
  an id or a time looked up first, `mixed` a display command joined to a query.
- **Agent requests carry no tool labels** (`tools_labelled: false`, empty
  `expected_tools`). Use the file for the fast path, where an agent request only
  has to be left alone; do not read stage A or stage B scores from it.
- The mix is not the main set's: a quarter of the agent requests are `near_tool`,
  chosen to be hard. Compare rates per class, not precision.
- **Do not tune against it.** Once a description or threshold is changed because
  of a failure here, it is a development set and new requests are needed.
  `tests/fastpath_agent/test_eval_label_sets.py` checks it shares no question with `labels.jsonl`.
- **Spent since 2026-11-15**: the gate fixes are developed against it. It is
  development data now, like `labels.jsonl`.

### The holdout set for the gate fixes

`fastpath_agent/data/holdout_labels.jsonl` holds 137 requests written on 2026-11-18, before any
gate change, as the blind test for the fixes to the fast path's gate (54 direct
commands, 83 agent requests). Unlike the 155 authored validation requests, their
author **had read** the packaged descriptions; they aim at what the validation
run showed passing the gate.

| `tag` | Route | Count | What |
|---|---|---|---|
| `near_tool` | agent | 59 | questions, remarks and negations about what a direct tool controls, about four per tool |
| `how_to`, `remark` | agent | 9 | "how do I...", "can you...", a comment on the display that asks for nothing |
| `control` | agent | 10 | ordinary questions, lookups, simulations, scenario edits |
| `mixed` | agent | 3 | a display command joined to a query |
| `command` | desktop | 44 | direct commands, phrased away from the descriptions' examples |
| `voice` | desktop | 6 | short commands after an unrelated earlier turn |
| `follow_up` | both | 4 + 2 | meaning taken from the earlier turn ("And back again."), plus two questions about the previous action |

- **Run it once, after the fix is chosen** on `labels.jsonl` and
  `validation_labels.jsonl`. Any change made after reading its results spends it.
- `follow_up` commands are there to catch a gate that drops the earlier turns:
  "And back again." means nothing alone.
- One author, unreviewed, like the validation set.

## Reading stage A

`full_recall` is the number that matters: the share of requests where every needed tool
was among those bound. A miss there is a turn the agent cannot complete, so the bar for
enabling the ranker is `full_recall >= 0.95` at a `top_k` that still removes at least
half of the tool schemas (`token_reduction >= 0.5`).

`k_needed` says how large `top_k` would have had to be, per record. Its p95 is the
`top_k` you would need to reach 95%.

## Tuning

The decision model scores each tool's question independently, so the question wording is
the lever. Variants live in `wordings.py`; scores are cached per wording in `.cache/`
(delete it after changing a wording or re-snapshotting the tools).

## Prompt layout and the model server's cache

| Script | What it answers |
|---|---|
| `cache_experiment.py` (`--cases` to pick some) | Time to first token when one part of the prompt changes between two requests |
| `eval_context_use.py` | Does the model still read the UI state when it rides on the user message? 12 state-dependent requests, two states, both placements |
| `eval_agent_step.py --mode full --sample 60 --context-placement system\|user` | Tool choice with a UI state present, in each position |

Run them from `rust/adsb-agent` (not from `eval/`), so the agent's `.env` is read.

## Decision model reading the tool descriptions

    ADSB_EVAL_TOOL_OVERRIDES=eval/fastpath_agent/fixtures/tool_overrides_v2.json \
        uv run python eval/fastpath_agent/eval_decision_gate.py

`fastpath_agent/decision_gate.py` builds one request of six `choice` questions (kind of
message, family of commands, a tool choice per family with the full
descriptions). The script scores it as a gate, as a veto on the embedding gate,
and re-applies both gates to the executor result files already in `results/`.
Results are in `rust/CLAUDE.md`.
